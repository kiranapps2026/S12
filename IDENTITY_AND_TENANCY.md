## 1. Identity Inventory

Every identity in the system, its format, scope, and purpose.

| Identity | Format | Scope | Purpose | Generated By |
|----------|--------|-------|---------|-------------|
| **tenant_id** | UUID v4 | Top-level | Permanent tenant isolation boundary. Never reused, never recycled. | S0 (Entry) |
| **workspace_id** | UUID v4 | Tenant-scoped | Logical workspace within a tenant. A user can belong to multiple workspaces. | API (workspace creation) |
| **membership_id** | UUID v4 | Tenant+Workspace | Represents user ↔ tenant/workspace ↔ role binding. NOT just user_id. | API (invitation/join) |
| **user_id** | UUID v4 | Tenant-scoped | Human user identity. Not globally unique — unique within tenant. | Auth provider |
| **worker_id** | UUID v4 | Workspace-scoped | Permanent worker identity (process, AI agent, cron job). | API (worker registration) |
| **worker_run_id** | UUID v4 | Worker-scoped | Single execution lifecycle of a worker process. | Worker startup |
| **connection_id** | UUID v4 | Workspace-scoped | Immutable identity for a provider account/token. | API (connection setup) |
| **capability_grant_id** | UUID v4 | Workspace-scoped | Records who granted a capability and at which scope. | API (grant) |
| **policy_version_id** | UUID v4 | Workspace-scoped | Exact policy version that authorized an execution. | S5 (resolution) |
| **provider_package_id** | Semver string | Global | Exact provider artifact/version used (e.g., `ghl-adapter@1.2.3`). | Deployment |
| **trace_id** | UUID v4 | Execution | Root identity for a user session/journey. Spans retries, clarifications. | S0 (Entry) |
| **request_id** | UUID v4 | Execution | Single inbound message identity. | S0 (Entry) |
| **execution_id** | UUID v4 | Execution | Primary operational lookup key. One plan run. | S9 (Plan) |
| **plan_id** | UUID v4 | Execution | Immutable plan after S10 confirmation. | S9 (Plan) |
| **step_id** | `step-{plan[:8]}-{NNNN}` | Execution | Logical step within a plan. May execute multiple times (retries). | S9 (Plan) |
| **attempt_id** | `att-{step_id}-{NNN}` | Execution | Single attempt of a step. Distinguishes retries. | S12 (Execute) |
| **provider_call_id** | `call-{UUID[:8]}` | Execution | Globally unique per adapter invocation. | S12 (Execute) |
| **resource_id** | UUID v4 | Workspace-scoped | External resource identity (contact, page, record). | Provider API |
| **api_key_id** | UUID v4 | Connection-scoped | API key/session identity, separate from user_id. | API (key creation) |

| **idempotency_key** | UUID v4 | Request | Canonical idempotency key = request_id. Used for duplicate detection. | S0 (Entry) |
| **lease_id** | UUID v4 | Execution | Worker ownership of an execution. For concurrent processing/recovery. | S12 (Execute) |
| **billing_account_id** | UUID v4 | Tenant-scoped | Billing account — separate from execution records. | API (billing setup) |
| **usage_event_id** | UUID v4 | Billing-scoped | Individual usage event for billing/auditing. | S2/S12 (resource consumption) |

### Identity Generation Rules

**ALL** identities follow these rules:

1. **System-generated only** — never from user input, never from LLM output
2. **UUID v4** unless format is specified otherwise
3. **Never recycled** — once assigned, an identity is permanent
4. **Scoped for uniqueness** — step_id includes plan prefix; attempt_id includes step reference
5. **Immutable after creation** — no identity field ever changes

## 2. Terminology: Worker vs Agent

These terms are NOT interchangeable. Using them incorrectly causes confusion in authorization, identity, and execution boundaries.

| Term | Definition | Scope |
|------|-----------|-------|
| **Worker** | Durable identity persisted in database, survives restarts. The unit of authorization, attribution, and lifecycle. | Architectural |
| **Worker Runtime** | Running process/container that embodies a Worker identity. Ephemeral. | Runtime |
| **Worker Pod** | Isolated runtime environment for a Worker Runtime. | Infrastructure |
| **Model** | LLM inference component (Claude, GPT, Gemini, etc.). Replaces dynamically per execution. | Provider |
| **Execution Strategy** | REFLEX / REACT / DAG / PLAN_EXECUTE / AGENTIC. How work is decomposed. | Architectural |
| **Agent** (deprecated in architecture docs) | Ambiguous. Use Worker, Worker Runtime, or Execution Strategy instead. | — |

**Never say "Worker equals Agent."** They are different concepts. A Worker is a durable identity. An Agent is a vague term that should not appear in architecture documentation.

## 3. Tenancy Hierarchy

### The Isolation Model

```
Tenant (top-level isolation boundary)
 │
 ├── Workspace A
 │    ├── User: Alice (owner)
 │    ├── User: Bob (member)
 │    ├── Connections: GHL account, Notion workspace
 │    ├── Capabilities: create_contact, create_page
 │    ├── Policies: workspace policy v1.2
 │    ├── Workers: ai-agent-1, cron-sync
 │    ├── Executions: trace-xxx → request-yyy → execution-zzz
 │    └── Billing: account-123
 │
 ├── Workspace B
 │    ├── User: Alice (admin)  ← Same user, different workspace
 │    ├── User: Charlie (member)
 │    ├── Connections: Airtable base
 │    ├── Capabilities: create_record
 │    ├── Policies: workspace policy v2.0
 │    └── Billing: account-456
 │
 └── Settings (tenant-level)
      ├── All users
      ├── All workspaces
      ├── Default policies
      └── Billing/payment
```

### Critical Rules

| Rule | Rationale |
|------|-----------|
| **tenant_id is the top-level boundary** | All data, all queries, all policies are tenant-scoped. Every SELECT includes `WHERE tenant_id = ?` |
| **Workspace is within a tenant** | A workspace cannot span tenants. A user can belong to multiple workspaces within the same tenant |
| **Same user, different workspace = different authorization** | Alice in Workspace A (owner) has different capabilities than Alice in Workspace B (admin) |
| **Isolation is enforced at DB level** | Row-level security (RLS) ensures no cross-tenant/workspace data leakage |
| **tenant_id never changes** | If a tenant is transferred, data moves — tenant_id does not |

### Tenant Lifecycle

```
ACTIVE → SUSPENDED → DELETED
            ↓
        (can reactivate)
```

| State | Meaning | Execution | Data |
|-------|---------|-----------|------|
| `ACTIVE` | Normal operation | Allowed | Full access |
| `SUSPENDED` | Temporarily disabled (billing, abuse) | Denied | Read-only for 30 days, then archived |
| `DELETED` | Permanently removed | Denied | Archived per data retention policy |

### Workspace Lifecycle

```
CREATED → ACTIVE → PAUSED → ARCHIVED → DELETED
              ↓         ↓
           (resume)  (can resume)
```

| State | Meaning | Execution | Data |
|-------|---------|-----------|------|
| `CREATED` | New workspace, being configured | Denied | Full access by creator |
| `ACTIVE` | Normal operation | Allowed | Full access |
| `PAUSED` | Temporarily disabled | Denied | Full access |
| `ARCHIVED` | Inactive but preserved | Denied | Read-only |
| `DELETED` | Permanently removed | Denied | Purged per retention |

## 4. Ownership Tree

This is the canonical ownership model. Every entity has exactly one owner. No entity exists without an owner.

```
Tenant
 └── Workspace
      ├── Membership → User
      │    └── (role, granted_capabilities, timestamps)
      │
      ├── Connections
      │    └── (provider, account, tokens, provider_package_id)
      │
      ├── Capabilities
      │    └── (capability_grant_id, granted_by, granted_to, scope)
      │
      ├── Policies
      │    ├── (policy_version_id, execution_modes, limits)
      │    └── PolicyVersion (immutable snapshot)
      │
      ├── Workers
      │    └── Worker Runs
      │         └── (worker_run_id, started_at, status)
      │
      ├── Executions
      │    └── Steps
      │         └── Attempts
      │              └── Provider Calls
      │
      ├── Usage/Billing
      │    ├── BillingAccount (billing_account_id)
      │    ├── UsageEvents (usage_event_id)
      │    └── Invoices
      │
      └── Audit Events
           └── (audit_event_id, timestamp, actor, action, target)
```

### Ownership Rules

| Rule | Rationale |
|------|-----------|
| Every workspace belongs to exactly one tenant | Prevents orphaned workspaces |
| Every execution belongs to exactly one workspace | Enables workspace-level quotas and billing |
| Every capability grant has a granting actor | Audit trail — who authorized what |
| Every policy version is immutable once created | Cannot silently change what authorized an execution |
| Every connection has a single owner workspace | Prevents credential sharing across workspaces |
| Every audit event has an immutable audit_event_id | Append-only, never modified |

## 5. Policy Hierarchy

The authorization chain from broadest to most specific. Each level can only restrict, never expand, the level above it.

```
Tenant Policy
 └── Workspace Policy
      └── User Role (RBAC)
           └── User Capability Grants
                └── Worker Capability Grants
                     └── Worker Management Settings (restrict-only; gate v10 C39)
                          └── Execution Mode (FAST/WORKFLOW/AGENTIC)
                               └── SafetyGate (S8)
```

> **Worker-management repair (RD-7, spec F1/F12):** "Worker Management Settings" is added below Worker Capability Grants. It can only restrict. In S12–S15 its only enforcement points are the S12 eligibility filters (WORKER_LIFECYCLE §13, §16); enforcing `restricted_capabilities` at S8 is an S0–S11 change and waits for change control.

### Tenant Policy

The broadest policy — applies to ALL workspaces within a tenant.

```python
@dataclass(frozen=True)
class TenantPolicy:
    """Tenant-level policy. Cannot be overridden by workspace policies."""
    tenant_id: str
    policy_version_id: str

    # Lifecycle
    state: Literal["ACTIVE", "SUSPENDED", "DELETED"]

    # Execution modes (disable at tenant level to block everywhere)
    execution_modes: dict[str, bool] = field(default_factory=lambda: {
        "FAST": True,
        "WORKFLOW": True,
        "AGENTIC": False,      # Disabled by default at tenant level
    })

    # Limits
    max_workspaces: int = 10
    max_users_per_workspace: int = 50
    max_workers: int = 100
    max_monthly_budget_minor_units: int = 1_000_000  # $10,000

    # Providers
    allowed_providers: list[str] = field(default_factory=lambda: ["ghl", "notion", "airtable", "google"])
    blocked_providers: list[str] = field(default_factory=list)

    # Features
    features: dict[str, bool] = field(default_factory=dict)

    # Emergency
    kill_switch: bool = False     # Tenant-level emergency stop
```

### Workspace Policy

More specific than tenant — applies to a single workspace.

### Worker Management Settings Contract (`workers.settings` JSONB)

> **Worker-management repair (spec Appendix B, corrected by review A-19 and RD-6):** every key is optional; a missing key falls back to tenant or global defaults; new keys need no migration.

| Key | Type | Rule |
|---|---|---|
| `skills_prompt` | string | Consumed at S2 (the LLM call). S2 is certified S0–S11, so this key is **inert** until an S0–S11 change is certified. |
| `rules` | list[string] | Business rules for the worker's LLM behavior; never an authorization input (I-007). |
| `restricted_capabilities` | list[capability_id] | Narrows the worker's grants; never widens them. **Live:** S12 eligibility filter 17b (gate v10 C39). Missing or empty = unrestricted. |
| `llm_model` | string | Must be in a tenant model allow-list that `TenantPolicy` does not have yet; **inert** until that field exists. Routing stays frozen per execution (DATA_CONTRACTS §42). |
| `execution_policy` | object | **Live:** `max_mutation` (`R`, `W`, `D` or `IRREVERSIBLE`): the worker is ineligible for a step whose frozen `effective_mutation` exceeds it (filter 17d). **Reserved, inert until post-S15:** `timeout_seconds`, `max_retries`, `retry_backoff` — when they land they may only lower MUTATION_SAFETY/RELIABILITY limits and never enable retries for IRREVERSIBLE or non-idempotent D. No per-worker circuit-breaker threshold: breakers are per provider. |
| `memory_policy`, `browser_policy`, `is_listed`, `listing_config`, `custom_fields` | object | Deferred features (post-S15). Not read in S12–S15. |

**Admin roles.** Worker-management bypasses (worker pause, worker activation, assignment — filters 12b, 13b, 14) apply when **the run's original principal** (`PrincipalChain.original_principal_id`) holds membership role `UserRole.OWNER` or `UserRole.ADMIN` **in the run's workspace**, read live at worker selection (audit round 2 B3). There is no bypass for a tenant or workspace pause. The spec's `TENANT_ADMIN` / `TENANT_OWNER` do not exist; VOCABULARY_INDEX uses `UserRole`.

**Autonomy.** The spec's per-grant `autonomy_level` (F20) is **not** added to `CapabilityGrant`, which is a frozen S0–S11 contract. `AutonomyLevel` (DATA_CONTRACTS §38) stays the only autonomy enum; a per-capability refinement, if added post-S15, is restrict-only (RD-14).

### Effective Policy Derivation

The SafetyGate at S8 computes the effective policy by intersecting all levels:

```python
def compute_effective_policy(
    tenant_policy: TenantPolicy,
    workspace_policy: WorkspacePolicy,
    user_role: UserRole,
    capability_grants: list[CapabilityGrant],
) -> EffectivePolicy:
    """Derive the single effective policy for an execution.

    Rule: each level can only RESTRICT, never expand, the level above.
    """

    # 1. Execution modes: ALL levels must enable the mode
    effective_modes = {}
    for mode in ["FAST", "WORKFLOW", "AGENTIC"]:
        tenant_allows = tenant_policy.execution_modes.get(mode, False)
        ws_allows = workspace_policy.execution_modes.get(mode, False)
        effective_modes[mode] = tenant_allows and ws_allows

    # 2. Limits: minimum across all levels
    effective_max_executions = min(
        workspace_policy.max_concurrent_executions,
        tenant_policy.max_workspaces * 10,  # tenant implicit limit
    )

    # 3. Capabilities: must be in both tenant ALLOWED and workspace ALLOWED
    # AND must have an explicit grant for this user
    # CRIT-014 fix: set("ALL") = {'A','L'} — never contains "ALL". Check string equality.
    tenant_allowed = tenant_policy.allowed_capabilities
    ws_allowed = workspace_policy.allowed_capabilities
    user_granted = {g.capability_id for g in capability_grants if g.is_active}

    if tenant_allowed != "ALL":
        effective_caps = set(tenant_allowed) if isinstance(tenant_allowed, list) else {tenant_allowed}
    else:
        effective_caps = "ALL"

    if ws_allowed != "ALL":
        ws_caps = set(ws_allowed) if isinstance(ws_allowed, list) else {ws_allowed}
        if effective_caps != "ALL":
            effective_caps = effective_caps & ws_caps
        else:
            effective_caps = ws_caps

    if effective_caps == "ALL":
        effective_caps = user_granted
    else:
        effective_caps = effective_caps & user_granted

    # 4. Providers: intersection of tenant + workspace
    tenant_providers = set(tenant_policy.allowed_providers) - set(tenant_policy.blocked_providers)
    ws_providers = set(workspace_policy.allowed_providers) - set(workspace_policy.blocked_providers)
    effective_providers = tenant_providers & ws_providers

    # 5. Kill switches: ANY active kill switch blocks execution
    if tenant_policy.kill_switch or workspace_policy.kill_switch:
        return EffectivePolicy(is_blocked=True, block_reason="Kill switch active")

    return EffectivePolicy(
        execution_modes=effective_modes,
        max_concurrent_executions=effective_max_executions,
        allowed_capabilities=effective_caps,
        allowed_providers=effective_providers,
        is_blocked=False,
    )
```

## 6. Authorization Chain

This is the chain the SafetyGate (S8) evaluates. Every level must pass.

```
Tenant Policy
    │  Is tenant ACTIVE? Kill switch off?
    │  Is execution mode allowed at tenant level?
    │  Is provider allowed at tenant level?
    ▼
Workspace Policy
    │  Is workspace ACTIVE? Kill switch off?
    │  Is execution mode allowed at workspace level?
    │  Is capability allowed at workspace level?
    │  Is provider allowed at workspace level?
    ▼
User Role (RBAC)
    │  Does user's role permit this action?
    │  Does user have execute permission?
    ▼
User Capability Grants
    │  Does the user have a GRANT for this specific capability?
    │  Is the grant active? Not expired?
    │  Is the grant's scope appropriate?
    ▼
Worker Capability Grants (if applicable)
    │  Does the worker have capability grants?
    │  (Workers execute on behalf of users/workspaces)
    ▼
Connection Authorization
    │  Is the provider connection active?
    │  Is the API key/session valid?
    ▼
Effective Policy
    │  (computed from all levels above)
    ▼
SafetyGate (S8) — 8 deterministic checks
```

### Worker Authorization (Separate from User Auth)

Workers execute on behalf of users but have **separate** authorization that does NOT inherit the user's capabilities.

```python
@dataclass(frozen=True)
class WorkerAuthorizationContext:
    """Authorization context for worker execution."""
    worker_id: str
    workspace_id: str
    tenant_id: str
    membership_id: str              # Worker's membership in workspace

    # What the worker is authorized to do (NOT from user grants)
    worker_capability_grants: list[CapabilityGrant]

    # The user whose request the worker is serving
    serving_user_id: str | None     # The user who triggered this execution

    # Delegation chain
    original_principal_id: str      # The user who ultimately authorized
```

**Rules**:
1. Worker capability grants are **independent** of user capability grants
2. A worker's capabilities are determined by its `CapabilityGrant` records, NOT by the user's grants
3. `serving_user_id` is for audit and billing — it does NOT expand worker capabilities
4. If a worker lacks a grant for a capability, the execution is DENIED regardless of the user's grants
5. **Assignment** (`workers.assigned_user_id`) restricts which `PrincipalChain.original_principal_id` a worker may serve; it never grants a capability. S12 eligibility filter 14 (gate v10 C39) applies it only when the original principal is a human user and the run is not EVENT_DRIVEN: event-driven and system runs skip it, and worker-delegated runs keep the human's assignment (audit round 2 B4). The admin bypass above applies.
5b. **Workspace boundary.** A worker serves only runs in its own workspace (`workers.workspace_id`, filter 4b; audit round 2 B7).
6. **Sub-agents** (post-S15): a child worker's `capability_profile` and grants are subsets of its parent's, and the PrincipalChain records the parent as `delegating_worker_id`.

> **Worker-management repair (RD-7, RD-13):** rules 5 and 6 added.

### Delegation and Impersonation Boundaries

```python
@dataclass(frozen=True)
class PrincipalChain:
    """Auditable chain of who authorized what."""
    original_principal_id: str         # The human user who initiated
    delegating_worker_id: str | None   # Worker that received the request
    executing_worker_id: str           # Worker that is executing
    target_connection_id: str          # Where the result goes
```

**Rules**:
1. A worker CANNOT impersonate a user — the `actor_type` is always "worker"
2. Delegation is explicit — the worker records who it is serving via `original_principal_id`
3. The original principal's capabilities do NOT flow to the worker
4. All mutations are attributed to `worker_id`, never to `user_id`
5. The PrincipalChain is immutable and stored with every execution
6. LLM output can NEVER modify the PrincipalChain
7. PrincipalChain is set at S0 and never changes

**Effective Authorization Formula**:
```python
def get_effective_authorization(ctx: AuthorizationContext) -> str:
    if ctx.actor_type == "user":
        return "user"
    elif ctx.actor_type == "system":
        return "system"
    elif ctx.actor_type == "worker":
        if ctx.actor_id is None:
            return "worker_system"     # Worker with no specific identity
        else:
            return "worker_delegated"  # Worker with identity (ctx.actor_id = worker_id)
```

## 7. Lifecycle States

### Tenant Lifecycle

```
ACTIVE ──→ SUSPENDED ──→ DELETED
   │           │
   │           └──→ ACTIVE (reactivation)
   │
   └──→ DELETED (force delete, bypasses SUSPENDED)
```

| State | Meaning | Who Can Transition | Grace Period |
|-------|---------|-------------------|--------------|
| `ACTIVE` | Normal operation | System | N/A |
| `SUSPENDED` | Billing failure, abuse, admin action | Admin, System | 30 days before auto-DELETED |
| `DELETED` | Permanently removed | Admin (force) | N/A |

### Workspace Lifecycle

```
CREATED → ACTIVE ←→ PAUSED → ARCHIVED → DELETED
```

| State | Meaning | Who Can Transition |
|-------|---------|-------------------|
| `CREATED` | New, being configured | Creator |
| `ACTIVE` | Normal operation | Admin |
| `PAUSED` | Temporarily disabled | Admin |
| `ARCHIVED` | Inactive, preserved | System (after 90 days PAUSED) |
| `DELETED` | Permanently removed | Owner |

### Membership Lifecycle

```
INVITED → ACTIVE → SUSPENDED → REMOVED
```

| State | Meaning |
|-------|---------|
| `INVITED` | Invitation sent, not yet accepted |
| `ACTIVE` | Active member |
| `SUSPENDED` | Temporarily disabled (security, leave) |
| `REMOVED` | No longer a member |

### Worker Lifecycle

```
REGISTERED → ACTIVE ←→ DRAINING → DRAINED → TERMINATED
```

| State | Meaning |
|-------|---------|
| `REGISTERED` | Created but not yet started |
| `ACTIVE` | Accepting executions |
| `DRAINING` | Finishing current executions, not accepting new |
| `DRAINED` | All work complete, ready to terminate |
| `TERMINATED` | Removed from pool (terminal) |

> **Worker-management repair (pre-existing defect found in review):** the former states STOPPED and DELETED contradicted STATE_TRANSITIONS §4, WORKER_LIFECYCLE §1 and gate Appendix A.5, which are authoritative. Pause and scheduled activation are **not** states: they are management columns checked at worker selection (gate v10 C39), so a paused worker stays ACTIVE.

### Connection Lifecycle

```
CREATED → ACTIVE ←→ DEGRADED → SUSPENDED → DELETED
```

| State | Meaning |
|-------|---------|
| `CREATED` | Token stored, not yet verified |
| `ACTIVE` | Healthy and operational |
| `DEGRADED` | Reachable but some operations failing |
| `SUSPENDED` | Auth failure, rate limited, admin disabled |
| `DELETED` | Tokens revoked, connection removed |

### Execution Lifecycle

```
PENDING → RUNNING → COMPLETED
                  → FAILED
                  → CANCELLED
                  → RECONCILING → COMPLETED | FAILED | DEAD_LETTER
                  → UNKNOWN → RECONCILING → ...
```

(See PIPELINE_STAGES.md §13 for complete state machine)

### Capability Lifecycle

```
implemented → enabled ←→ disabled → retired
                ↓
           (can re-enable)
```

| State | Meaning | Can Resolve? |
|-------|---------|-------------|
| `implemented` | Defined but not yet active | No |
| `enabled` | Active and resolvable | **Yes (only state that allows resolution)** |
| `disabled` | Temporarily inactive | No |
| `retired` | Permanently inactive | No |

## 9. Cross-Cutting Concerns

### 8.1 Multi-Workspace Users

**Rule**: A user can belong to multiple workspaces. Authorization ALWAYS evaluates the active `(tenant_id, workspace_id, user_id)` context, NOT just `user_id`.

```python
# WRONG — only checks user_id
if user.has_capability("create_contact"):
    allow()  # User might have it in Workspace A but not B

# CORRECT — checks full context
if membership.has_capability(
    tenant_id=context.tenant_id,
    workspace_id=context.workspace_id,
    user_id=context.user_id,
    capability="create_contact",
):
    allow()
```

### 8.2 Cross-Workspace Isolation

| Rule | Enforcement |
|------|-------------|
| Data from Workspace A is NEVER visible to Workspace B | DB RLS on every query |
| Connections are NOT shared between workspaces | Each workspace has its own connections |
| Capability grants are NOT shared between workspaces | Scoped to workspace |
| Billing is per-workspace with tenant-level aggregation | Separate billing_account_id per workspace |
| Workers are NOT shared between workspaces | Worker is scoped to one workspace |

### 8.3 RBAC Integration into SafetyGate

The SafetyGate (S8) now evaluates the full authorization chain:

```python
class SafetyGate:
    """8 deterministic checks, ALL must pass, FAIL-CLOSED."""

    def evaluate(self, context: AuthorizationContext, effective_policy: EffectivePolicy) -> SafetyResult:
        checks = [
            # G4a: Tenant-level checks
            self.check_tenant_active(context.tenant_id),
            self.check_tenant_kill_switch(context.tenant_id),
            self.check_execution_mode_allowed(effective_policy, context.execution_mode),

            # G4b: Workspace-level checks
            self.check_workspace_active(context.workspace_id),
            self.check_workspace_kill_switch(context.workspace_id),
            self.check_workspace_capability_allowed(context, effective_policy),

            # G4c: Actor-level checks
            self.check_user_role_permission(context),
            self.check_capability_grant(context),
        ]
        # ALL must pass
```

### 8.4 Emergency Kill Switches

```python
@dataclass(frozen=True)
class KillSwitch:
    """Emergency stop — checked at S8 before anything else."""
    tenant_id: str
    workspace_id: str | None  # None = tenant-level kill switch
    activated_by: str         # user_id or "system"
    activated_at: str         # ISO 8601 UTC
    reason: str
    auto_expire_at: str | None  # Optional auto-reactivation

# Check at S8, FIRST check before anything else:
def check_kill_switch(context: AuthorizationContext) -> CheckResult:
    if db.get_tenant_kill_switch(context.tenant_id):
        return CheckResult(passed=False, reason="Tenant kill switch active")
    if db.get_workspace_kill_switch(context.workspace_id):
        return CheckResult(passed=False, reason="Workspace kill switch active")
    return CheckResult(passed=True)
```

> **Worker-management repair (RD-5; audit round 2 B6):** **pause ≠ kill switch.** A tenant or workspace pause (`paused_until`) is checked at **S0.1** (S0–S11 ruling R-P, before any S1–S11 work) and again at S12 entry, and blocks **new** runs; a worker pause blocks **new** leases. A pause never cancels running work (drain semantics). The kill switch stops now: remaining steps are CANCELLED with `kill_switch_engaged` (gate C23). Pause and activation times are compared with database `NOW()` (§11 Rule 1). Worker groups are post-S15.

## 10. Implementation Rules

### Rule 1: Lock Identities Now

Every identity listed in Section 1 is frozen. Changing an identity format or scope requires architectural review because it touches every downstream system.

### Rule 2: Always Query with Full Context

Every database query includes tenant_id AND workspace_id. Never query by user_id alone.

```python
# CORRECT
db.execute("SELECT * FROM executions WHERE tenant_id = ? AND workspace_id = ?", ...)

# WRONG
db.execute("SELECT * FROM executions WHERE user_id = ?", ...)
```

### Rule 3: Policy is Evaluated as Intersection

Workspace policy can only RESTRICT tenant policy, never expand it. User grants can only add capabilities that are already allowed by both policies.

### Rule 4: FrozenBindingIdentity Captures Policy Versions

At S5, the FrozenBindingIdentity records the exact `tenant_policy_version_id` and `workspace_policy_version_id` that authorized the execution. If policy is later changed, existing executions still reference the version that authorized them.

### Rule 5: Worker Identity is Separate from User Identity

Workers execute on behalf of a workspace, not on behalf of a specific user. Workers have their own capability grants, independent of user grants. When a worker executes, `actor_type = "worker"` and `actor_id = worker_id`.

### Rule 6: Connection Identity is Immutable

A connection's identity never changes, even if the underlying token is rotated. Token rotation creates a new token record linked to the same connection_id.

### Rule 7: Audit is Append-Only

Every identity transition, policy change, capability grant, and execution event produces an immutable audit_event_id. Audit records are NEVER modified or deleted.

## 11. Time and Clock Correctness

All time-sensitive decisions in the kernel must use server-authoritative time. Worker-local clocks are untrusted and must never be the basis for any distributed decision.

### Rule 1: Server-Authoritative Time

**Rule**: "All timestamps in the kernel use server-authoritative time (database NOW() or dedicated time service)."

Every timestamp stored in the database, used in policy decisions, or included in audit events must come from the server, not from the worker that initiated the request.

```python
# CORRECT — server timestamp
created_at = db.now()  # Database NOW()
# or
created_at = time_service.now_utc()

# WRONG — worker-local clock
created_at = datetime.now(timezone.utc)  # Worker's local clock — DO NOT USE
```

### Rule 2: Worker-Local Clocks Are Untrusted

**Rule**: "Worker-local clocks are used only for local measurements."

Worker-local clocks may be used for:
- Measuring local elapsed time (e.g., "this step took 2.3 seconds")
- Local scheduling within a worker process
- Logging for debugging purposes (clearly labeled as worker-local)

Worker-local clocks must NOT be used for:
- Timestamps stored in the database
- Lease expiration calculations
- Heartbeat freshness evaluation
- Any authorization or policy decision

### Clock Skew Tolerance

**Rule**: "Maximum tolerated clock skew: 5 seconds. If worker clock differs from server clock by > 5s → warn. If worker clock differs from server clock by > 30s → reject (stale worker)."

| Skew | Action |
|------|--------|
| <= 5 seconds | Normal — no action |
| > 5 seconds | Warn in logs, flag worker for monitoring |
| > 30 seconds | Reject — worker is stale, refuse to accept new executions |

```python
def validate_worker_clock(worker_id: str, worker_reported_time: datetime) -> ValidationResult:
    """Check if worker's clock is reasonably synchronized with server."""
    server_time = db.now()
    skew = abs((server_time - worker_reported_time).total_seconds())

    if skew > 30:
        return ValidationResult(
            passed=False,
            reason=f"Worker clock skew {skew:.1f}s exceeds 30s threshold — stale worker"
        )
    elif skew > 5:
        log.warn("worker_clock_skew", worker_id=worker_id, skew_seconds=skew)
        # Continue but flag for monitoring

    return ValidationResult(passed=True)
```

### Monotonic Timing for Leases

Lease validity uses monotonic elapsed time, not wall-clock timestamps. This prevents clock skew from affecting lease expiration.

```python
@dataclass(frozen=True)
class Lease:
    """Worker ownership of an execution."""
    lease_id: str
    execution_id: str
    worker_id: str
    worker_run_id: str

    # Server-authoritative timestamps (wall-clock)
    acquired_at: str        # Server NOW() when lease was granted
    expires_at: str         # Server NOW() + lease_duration_seconds

    # Monotonic elapsed time (for worker-side tracking)
    lease_duration_seconds: int = 300  # 5 minutes

    # Worker reports elapsed time, server validates against monotonic clock
    worker_elapsed_seconds: int | None = None  # From worker's monotonic clock

    # Server-side monotonic tracking
    server_monotonic_start: float | None = None  # time.monotonic() at acquisition
```

**Key principle**: When the server grants a lease at `acquired_at`, it records `server_monotonic_start = time.monotonic()`. When checking lease validity, the server computes `elapsed = time.monotonic() - server_monotonic_start` and compares against `lease_duration_seconds`. This is immune to wall-clock adjustments (NTP jumps, DST, manual changes).

### Heartbeat Processing

**Rule**: "Heartbeat processing uses server receipt time, not worker send time."

When a worker sends a heartbeat, the server records the heartbeat using the server's receipt time, not the timestamp embedded in the heartbeat message.

```python
def process_heartbeat(lease_id: str, worker_heartbeat: WorkerHeartbeat) -> HeartbeatResult:
    """Process worker heartbeat — server-authoritative time only."""
    # Server receipt time — THIS is the timestamp we use
    received_at = db.now()

    # Worker's claimed time is ignored for freshness calculations
    # (used only for diagnostic comparison)
    worker_claimed_time = worker_heartbeat.timestamp

    # Check clock skew for monitoring
    skew = abs((received_at - worker_claimed_time).total_seconds())
    if skew > 5:
        log.warn("heartbeat_clock_skew", lease_id=lease_id, skew_seconds=skew)

    # Lease freshness based on SERVER time
    lease = db.get_lease(lease_id)
    last_heartbeat_server_time = lease.last_heartbeat_at  # Server-recorded time
    elapsed_since_heartbeat = (received_at - last_heartbeat_server_time).total_seconds()

    if elapsed_since_heartbeat > HEARTBEAT_TIMEOUT_SECONDS:
        return HeartbeatResult(status="stale", action="revoke_lease")
```

### Rule 3: No Worker-Local Time in Distributed Decisions

**Rule**: "No distributed lease decision uses worker-local time."

Any decision that affects multiple workers or requires coordination must use server-authoritative time exclusively.

| Decision | Time Source |
|----------|-------------|
| Lease grant/expiration | Server monotonic elapsed time |
| Heartbeat freshness | Server receipt time |
| Stale worker detection | Server time comparison |
| Execution timeout | Server-authoritative duration |
| Audit event timestamps | Server NOW() |
| Policy effective time | Server NOW() |
| Rate limiting windows | Server time |

### Validation Test

Reference test: `test_clock_correctness()`

This test validates:
1. Server timestamps are used for all database records
2. Worker-local timestamps are rejected from policy decisions
3. Monotonic timing correctly measures lease duration regardless of wall-clock changes
4. Clock skew detection triggers warnings at 5s and rejection at 30s
5. Heartbeat processing uses server receipt time

## Guardrail Precedence Order

When multiple guardrails could block an operation, this is the precedence order (highest authority first):

```
1.  Identity           — Is the actor authenticated?
2.  Tenant Isolation   — Is the tenant active? Kill switch off?
3.  Kill Switch        — Any active kill switch blocks execution
4.  Authorization      — Does the actor have capability grants?
5.  Capability Scope   — Is the capability in scope for this execution mode?
6.  Policy             — Do tenant + workspace policies allow this?
7.  Risk/Mutation      — Does effective_risk exceed threshold? Is mutation allowed?
8.  Budget             — Is budget available? Is reservation valid?
9.  Reliability        — Circuit breaker, timeout, retry budget
10. Execution          — Can the step execute? Are dependencies met?
```

Lower-priority guardrails cannot override higher-priority ones. If Identity fails, no other guardrail is evaluated.
