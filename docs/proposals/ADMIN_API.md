# Phase B4: the administration API

Routes under `/api/v1/admin` (Bearer API key). Everything is scoped to the caller's tenant.

| Area | Routes |
|---|---|
| API keys | `POST /api-keys` (returns the key ONCE), `GET /api-keys`, `DELETE /api-keys/{key_id}` |
| Webhook / MCP endpoints | `POST /endpoints` (returns the signing secret ONCE and the URL path), `GET /endpoints`, `POST /endpoints/{id}/rotate` (optional `{"grace": "24 hours"}`), `DELETE /endpoints/{id}` |
| Event schemas | `PUT /event-schemas/{source_system}/{event_type}` body `{"schema": {...}}` (a new version), `GET /event-schemas`, `GET /event-schemas/{source_system}/{event_type}`, `DELETE /event-schemas/{source_system}/{event_type}/{version}` (deactivate) |
| Schedules | `POST /schedules`, `GET /schedules`, `DELETE /schedules/{id}` (deactivate) |
| Audit | `GET /audit?limit=100` |

Requests carry NO identity fields (bodies with extra fields are rejected): a credential or schedule is created from a
`membership_id` and a `connection_id`; the service derives the user and workspace from them and checks that they
belong to the caller's tenant, agree with each other and are active.

## Rules (each has a test)

- **Who may administer:** an ACTIVE `owner` or `admin` membership, an active user in an active tenant, checked live on
  every request (a role removed a moment ago is refused now). Others get `403 admin_required`.
- **Role ceiling:** an administrator can create keys, endpoints and schedules only for memberships whose role is not
  higher than their own (an admin cannot mint an owner's key: `403 role_exceeds_yours`).
- **Tenant scope:** another tenant's ids are `404`; tables without row-level security (`api_keys`,
  `webhook_credentials`, `event_schedules`) are always filtered by tenant in the service.
- **Secrets are shown once:** the key or signing secret is in the creating response only. Listings, the audit trail and
  the database never contain a secret; only its hash (keys) or ciphertext (secrets) is stored.
- **Audit in the same transaction:** every mutation and its `admin_audit` row are one transaction, so a change without a
  record cannot happen. `admin_audit` is append-only (trigger + no DELETE privilege), tenant-scoped, holds ids, versions
  and labels only.
- **Schemas:** the same subset the gateway enforces; anything else is `422`, oversize is `413`. Deactivating every version
  of a type means its events are refused. A schedule can only be created for a `cron` event type that is registered and
  whose schema its payload satisfies (a schedule that could never run is refused now).
- **Endpoints need `WEBHOOK_KEK`**; without it those routes answer `503`, the rest still work.

## First administrator (bootstrap)

There must be a first key. In the database make one membership `admin` or `owner`
(`UPDATE memberships SET role = 'owner' WHERE membership_id = ...`) and create its key with the CLI:
`python -m src.main --issue-api-key TENANT WORKSPACE USER MEMBERSHIP CONNECTION SCOPE`. From then on use the API.

## Working rulings (owner may overrule)

| Ruling | Decision |
|---|---|
| R-BH | Administration is a role of the membership (`owner`/`admin`), checked live; there is no separate admin credential. |
| R-BI | The role ceiling above (nobody can grant more than they hold). |
| R-BJ | Secrets once, audit atomic and append-only. |
| R-BK | A webhook/MCP endpoint or schedule acts as a dedicated service user (R-AT). Superseded by R-BM: it is now enforced. |
| R-BL | Schedule ids are generated by the server (they are global keys). |
| R-BM | `users.is_service` (migration 013) marks a service identity. Endpoints and schedules can only be issued for a service user (`409 not_a_service_user`); API keys may be issued for either. |
| R-BN | User/membership/connection/grant management (`admin_access.py`, routes under `/api/v1/admin`): ids are server-generated (`usr_`, `mem_`, `conn_`, `grant_`, `ws_`); the role ceiling applies to every target (nobody touches a user whose role exceeds theirs, nobody assigns a role above their own); nobody changes their own role, status or membership (`403 cannot_change_yourself`); the last active owner cannot be demoted, removed or suspended (`409 last_owner`, defence in depth). |
| R-BO | Memberships and connections are deactivated, never deleted (rows stay for the record); the holder loses access immediately because admin and identity checks are live. |
| R-BP | Grants only for `PRODUCTION_ENABLED` capabilities, to an active user with an active membership in that workspace; a duplicate active grant is `409`; `expires_at` must be timezone-aware and in the future; grants of `D`/`IRREVERSIBLE` capabilities need the `owner` role (`403 owner_required_for_high_impact`). |

## Routes for access management

`POST/GET /workspaces`; `POST/GET /users`, `POST /users/{id}/status`; `POST/GET /memberships`, `POST /memberships/{id}/role`,
`DELETE /memberships/{id}`; `POST/GET /connections`, `POST /connections/{id}/revoke`; `GET /capabilities`;
`POST/GET /grants`, `DELETE /grants/{id}`. Every mutation writes its `admin_audit` row in the same transaction.
