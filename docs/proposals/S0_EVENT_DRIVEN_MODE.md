# S0 event-driven mode (EVENT_DRIVEN) — implementation and rulings needed

Owner decision (given): **webhooks authenticate with a per-endpoint HMAC signing secret**
(PIPELINE_STAGES §2, EVENT_GATEWAY_AND_ROUTER §11, SECURITY §11).

## What is built

`POST /api/v1/webhooks/{source_system}/{endpoint_id}`, header `X-Signature: t=<unix>,v1=<hex>`,
`v1 = HMAC-SHA256(secret, "<t>." + raw body)`.

1. **Authenticate** – the endpoint id selects the credential (and thereby the tenant, workspace
   and user); only a valid signature proves it. Unknown endpoint, wrong source, malformed header
   and wrong signature are one indistinguishable `401`. Comparison is constant-time.
2. **Validate** – timestamp within ±300 s of server time (`400 stale_timestamp`, reported only
   after the signature is proven); body ≤ 64 KiB (`413`); JSON object with a `type` of
   `[A-Za-z0-9_.:-]{1,64}`.
3. **Store** – raw payload in `event_log`, one row per `(tenant, idempotency_key)`
   (`webhook:{source_system}:{source id}` if the sender gives an `id`, otherwise
   `…:{timestamp}.{sha256(body)}`). A repeat is acknowledged (`reason: duplicate_event`) and not run again.
4. **Envelope** – `EventEnvelope` (DATA_CONTRACTS §46). `event_id` and `correlation_id` are
   generated by the gateway. `tenant_id`/`workspace_id` come from the credential (I-022).
5. **Run** – the same single pipeline as a user request. S0: `event_id` → `task_id`
   (S2 keeps it), `correlation_id` → `conversation_id`, `trace_id`/`request_id` still generated
   by S0 (the spec's "correlation_id → trace_id" contradicts "trace_id is never from the event";
   the second rule wins). S1 sees `Event <type> from <source>: <payload json>` as ordinary
   untrusted text: sanitised, size-limited, evasion-proof injection detection. S8 checks the
   credential's user, connection, grant and scope exactly as for a person.

Secrets: AES-256-GCM under a per-record DEK, DEK wrapped by a KEK from `WEBHOOK_KEK`
(never in the database), plaintext held in a `bytearray` and overwritten after the check,
never logged. Rotation: one `active` + at most one `retiring` (24 h grace) per endpoint;
a retiring match is logged.

## Deviations from DATABASE.md — need an owner ruling

| # | Deviation | Why |
|---|---|---|
| E1 | `webhook_credentials` gains `endpoint_id`, `workspace_id`, `user_id`, `membership_id`, `connection_id`, `resource_scope` | The spec's table has no way to find the credential *before* the tenant is known, nor an identity for S0/S8 (`user_id` "from Event Gateway auth"). Mirrors `api_keys`. |
| E2 | `event_log` stores the payload in a `payload BYTEA` column; `TIMESTAMPTZ` instead of `REAL` | `payload_ref = pg:event_log.<id>` needs the payload somewhere; consistency with every other table. |
| E3 | The run is synchronous (S0–S11) and answers `200` with the outcome, not `202` | There is no queue, router or worker (S12+). |
| E4 | `webhook_credentials` has no RLS (pre-tenant lookup, like `api_keys`) | The spec's `system_worker_role` does not exist yet. It holds only ciphertext. |
| E5 | Only `source = webhook`; schedule, MCP and API events are not built | Out of scope for the chosen mechanism. |

## Not built

Subscription matching / EventRouter, schema registry per event type, `event_log` retention,
KEK rotation tool (re-wrap of `wrapped_dek`), an admin API to issue/rotate secrets
(`PostgresWebhookCredentials.issue` / `.rotate` exist and are tested).
